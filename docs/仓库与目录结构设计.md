## 0. 本版修订摘要

相对 06 号文档 §3，本版做了 10 处调整：

| # | 06 号文档原文 | 本版调整 | 原因 |
|---|---|---|---|
| 1 | `internal/domain/` 与 `internal/auth/`、`internal/order/` 并列，未说明两者关系 | `domain/` 降级为**共享内核**；业务域一律采用**垂直切片** | 原文同时含分层与切片两种信号，必须收敛为一种 |
| 2 | 无 `openapi/` 目录 | 新增 `openapi/`，按域拆分 paths | §7 要求「OpenAPI 作为唯一接口契约」，必须有物理落点 |
| 3 | 仅 `upstream/foxssl/` | 新增 `internal/upstream/payment/` | §4.2、§7 存在支付渠道，同样需要可 Mock、可替换 |
| 4 | 无基础设施装配层 | 新增 `internal/platform/` | `config/` 只解决配置读取，不解决连接与生命周期 |
| 5 | `internal/queue/` 与 `internal/task/` 并存 | 合并为 `internal/jobs/` | 两者职责重叠、边界无法自证 |
| 6 | `internal/admin/` 定位模糊 | 限定为 RBAC / 审计 / 调账审批等**横切能力** | 否则会演变成第二个 service 层 |
| 7 | `packages/product-rules` 与 §4.3「后端必须统一校验规则」重复 | 前端包只保留**展示映射**，校验规则后端唯一真源 | 防止前后端规则漂移 |
| 8 | `deploy/` 空置，根目录无 compose | 根 `docker-compose.yml`（开发）+ `deploy/`（生产） | 消除空目录，职责分层 |
| 9 | 无根配置文件 | 补 `Makefile`、`.gitignore`、`.env.example`、`.nvmrc`、`pnpm-workspace.yaml` | 单仓形态的必需件 |
| 10 | 无脚本目录 | 新增 `scripts/` | 契约生成与 CI 校验需要落点 |

## 1. 已确认的结构决策

| 编号 | 决策 | 取值 | 说明 |
|---|---|---|---|
| D1 | Go 服务端内部包组织 | **垂直切片** | 每个业务域一个包，包内自带 handler/service/repository/model |
| D2 | 仓库形态 | **pnpm 单仓** | `apps/` + `packages/` 由 pnpm workspace 管理；`server/` 独立 `go.mod` |
| D3 | 接口契约真源 | `openapi/openapi.yaml` | 唯一真源，Go 侧校验实现、TS 侧生成类型 |
| D4 | 产品规则真源 | 后端唯一真源，通过 API 下发 | 前端不做校验，只做展示映射（**待确认，见 §8**） |
| D5 | 开发环境编排 | 根 `docker-compose.yml` | 仅 MySQL 8 + Redis 7 |
| D6 | 生产编排 | `deploy/` | Phase 5 填充，Phase 0 只放 Dockerfile |

### D2 的补充说明

`server/go.mod` 放在 `server/` 子目录而非仓库根，理由是避免 Go 工具链遍历 `node_modules`（数万文件会导致 `go build`、`gopls` 显著变慢）。前端与后端通过 `openapi/` 契约交换信息，不通过 Go 包共享代码。

## 3. Go 服务端包规范（D1 落地）

### 3.1 垂直切片包的标准构成

每个业务域包（`auth`、`user`、`wallet`、`recharge`、`payment`、`product`、`order`、`certificate`、`webhook`）遵循同一结构：

| 文件 | 职责 | 约束 |
|---|---|---|
| `model.go` | 领域实体与值对象 | 只依赖 `internal/domain`，不 import 其他域包 |
| `repository.go` | 数据访问，接口与实现同文件 | 只依赖 `platform/mysql`、`platform/redis` |
| `service.go` | 业务规则、事务编排 | 依赖本包 Repository + 其他域 Service 接口 + upstream Client |
| `handler.go` | HTTP 参数解析与响应 | 只依赖本包 Service，不含业务判断 |
| `service_test.go` | 业务规则单测 | 用 `mock_client.go` 替代真实上游 |

### 3.2 依赖方向（强制）

```text
cmd/{api,worker,cron}
   │
   ├─→ internal/server            router / middleware / response
   │        │
   │        └─→ internal/<域>.Handler
   │                   │
   │                   └─→ internal/<域>.Service
   │                             ├─→ internal/<域>.Repository ─→ platform/mysql、platform/redis
   │                             └─→ internal/upstream/{foxssl,payment}.Client（接口）
   │
   └─→ internal/jobs ─→ internal/<域>.Service
```

### 3.3 五条不可违反的规则

1. **禁止跨域直连 Repository。** 域包之间只能通过对方暴露的 Service 接口调用。`order` 需要扣款时调用 `wallet.Service`，不得直接查 `wallet_accounts`。
2. **`internal/domain/` 不得 import 任何业务域包。** 它是最底层共享内核，一旦反向依赖就形成环。
3. **Handler 不得直接调用 upstream。** 所有上游调用必须经过 Service，便于加入重试、幂等、日志和补偿。
4. **`platform/` 只被 Repository 与 `bootstrap` 依赖。** 业务代码不直接持有 `*sql.DB`。
5. **跨域事务由发起方持有。** 事务句柄通过 `context.Context` 传递，不通过全局变量。

### 3.4 后台接口的归属

后台（Ant Design Pro）调用的业务接口**不集中在 `internal/admin/`**，而是分散在各自域包内，以 `admin_handler.go` 命名区分：

```text
internal/order/admin_handler.go        订单查询、同步状态、取消、重签
internal/product/admin_handler.go      产品上下架、价格维护
internal/wallet/admin_handler.go       账本查询、调账
```

`internal/admin/` 只承载三件事：

- RBAC 角色权限模型与判定
- 管理员操作审计记录
- 人工调账的多级审批流（提交 → 财务审核 → 主管复核 → 写账本）

这样同一份订单查询逻辑只有一处实现，避免后台接口与用户接口逻辑分叉。

## 4. 前端 workspace 规范（D2 落地）

### 4.1 pnpm-workspace.yaml

```yaml
packages:
  - "apps/*"
  - "packages/*"
```

根 `package.json` 需声明 `"packageManager"` 字段锁定 pnpm 版本，`.nvmrc` 锁定 Node 大版本，避免 Next.js 与 Umi 两套构建体系在 Node 版本上打架。

### 4.2 契约生成链路（D3 落地）

```text
openapi/openapi.yaml                     唯一真源
        │
        ├─→ Go 侧：接口实现校验（CI 中比对路由与 schema）
        │
        └─→ scripts/gen-api-types.sh
                │
                └─→ packages/api-types/src/generated/
                        │
                        ├─→ apps/web/src/lib/api/
                        └─→ apps/admin/src/services/
```

**约束：**

- `packages/api-types/src/generated/` 为生成物，禁止手工修改，`scripts/check-generated.sh` 在 CI 中重新生成并比对，不一致即失败。
- 统一响应包装 `{code, message, data}` 在 `openapi/components/responses.yaml` 中定义一次，所有路径复用。
- 前后端字段以 schema 为唯一依据，任何一方需要新字段时先改 `openapi/`。

### 4.3 产品规则的职责划分（D4 落地）

| 层 | 职责 | 不做 |
|---|---|---|
| `server/internal/product/rules/` | 全部校验规则：EV 不支持通配符、通配符不支持文件验证、GlobalSign 不支持邮件验证等 | — |
| 产品接口响应 | 下发该产品在当前选择下**可用**的年限、算法、DCV 方式 | — |
| `packages/product-rules/` | 仅把枚举值映射为中文文案与图标 | 不做任何合法性判断 |

前端表单的选项由接口下发结果驱动，而非本地规则推导。这样规则变更只需改后端一处，前端无需发版。

## 5. 配置与工具链

### 5.1 根 Makefile 目标

```text
make dev-up          启动 MySQL + Redis
make dev-down        停止并清理
make migrate-up      执行数据库迁移
make migrate-down    回滚一步
make migrate-create  新建迁移文件
make gen             生成 API 类型与请求层
make gen-check       CI 校验生成物未漂移
make lint            go vet + golangci-lint + eslint
make test            单元测试
make build           构建 api / worker / cron 三个二进制
make run-api         本地启动 API
make run-worker      本地启动 Worker
make run-cron        本地启动 Cron
```

### 5.2 .env.example 变量清单

```text
APP_ENV
APP_PORT
APP_BASE_URL

MYSQL_DSN
REDIS_ADDR
REDIS_PASSWORD

JWT_SECRET
JWT_ACCESS_TTL
JWT_REFRESH_TTL

FOXSSL_BASE_URL
FOXSSL_API_KEY
FOXSSL_WEBHOOK_SECRET

PAYMENT_PROVIDER
PAYMENT_APP_ID
PAYMENT_PRIVATE_KEY
PAYMENT_WEBHOOK_SECRET

SMTP_HOST
SMTP_PORT
SMTP_USER
SMTP_PASSWORD

LOG_LEVEL
```

**硬约束：** `FOXSSL_API_KEY`、`PAYMENT_PRIVATE_KEY` 仅存在于服务端环境变量或密钥管理系统，禁止进入前端构建产物、日志输出和错误响应体。`.env` 必须写入 `.gitignore`。

### 5.3 版本锁定

- `.nvmrc` 与根 `package.json` 的 `engines` 字段保持一致的 Node 大版本。
- `server/go.mod` 的 Go 版本以本机实际安装的稳定版为准，在 Phase 0 执行 `go version` 确认后写入。
- 生产依赖使用精确版本，不使用 `^` / `~` 浮动。

## 9. Phase 0 落地清单

1. `git init` + 根配置文件（`.gitignore`、`.editorconfig`、`.nvmrc`、`.env.example`、`README.md`）
2. `pnpm-workspace.yaml` + 根 `package.json` + `Makefile`
3. `openapi/openapi.yaml` 骨架，含统一响应包装与 auth 两条路径，作为契约起点
4. `server/`：`go.mod` + `cmd/{api,worker,cron}` 三入口 + `internal/config` + `internal/platform` + `internal/server`
5. `docker-compose.yml`（MySQL 8 + Redis 7），`make dev-up` 可启动
6. `server/migrations/000001_init_users.{up,down}.sql`，`make migrate-up` 可执行，验证迁移链路
7. `scripts/gen-api-types.sh` + `packages/api-types`，`make gen` 可产出类型
8. `apps/admin` 用 Ant Design Pro 脚手架初始化，`apps/web` 用 Next.js 初始化，均能消费 `@c-ssl/api-types`
9. 一个端到端冒烟：`/api/v1/products` 返回真实数据，后台 ProTable 能拉到

**验收标准：** 第 9 步跑通即认为 Phase 0 完成。此阶段不写任何业务逻辑，FoxSSL 使用 `mock_client.go`。

## 10. 与 06 号文档验收标准的对应

06 号文档 §11 的 10 条验收标准中，与本目录结构直接相关的 4 条：

| 06 号 §11 条目 | 本目录结构的支撑点 |
|---|---|
| 3. 余额不足时无法下单 | `order.Service` 通过 `wallet.Service` 接口扣款，不绕过 |
| 5. 同一订单重复提交不创建重复 FoxSSL 订单 | 幂等键落在 `order.Repository` + Redis，Handler 不参与 |
| 6. 产品规则在后端校验 | `internal/product/rules/` 为唯一真源，前端包无校验能力 |
| 10. API Key 不出现在前端和普通日志 | `upstream/foxssl/http_client.go` 统一注入密钥，`logger` 中间件过滤敏感字段 |
